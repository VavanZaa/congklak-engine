# Finish the five capped H14 roots

This is an investigation-only continuation of the sealed six-root horizon probe. Exactly its five requested-H14 budget rejections are selected. All six original wrapped roots, ownership, H8/H10/H12 reference items, prior H12/H14 attempts and the one completed old H14 item remain unchanged. The fixed policy/value model is `data/quality-train-v1/model.json`, SHA-256 `bc1160e99f419b3c1052ea87b28145b622639e6e76a49127c388ab4926d67558`.

The production schedule performs all five H14 searches with a 250,000,000-node cap first. Only roots still rejected receive H14 at a 1,000,000,000-node fallback cap, in sorted key order. Successful initial roots never enter fallback. No further expansion, H16 search, training, data ingestion or default-engine promotion is authorized. The maximum new production allocation is 6,250,000,000 nodes; earlier probe work and fixture work are separate.

The unchanged native teacher uses time limit zero, TT16 MiB, PVS, a 512 MiB memory setting and complete iterative histories. Every retained report is a completed report at its own explicit depth. Only completion of requested H14 produces a full H14 label. Every overlapping completed depth must agree in action Q values and best moves with all sealed old histories and the other new tier. Values and moves may change between different depths. H14 remains a finite-horizon estimate, not solved game truth.

If fallback also caps, the closed journal records `status="budget_exhausted"`, `scope_finished=false` and exact unresolved keys. An auxiliary H13 report never becomes a requested H14 label. Such a result does not fulfill the goal of finishing all five roots.

`data/horizon-finish-v1/work.sqlite3` uses an exclusive writer, WAL/FULL durability and atomic root/tier attempt plus optional label commits. Completed attempts, including rejections, are never recomputed. An interruption during an uncommitted root restarts that root; committed prefixes survive. Both tiers expose flushed precommit and postcommit barriers for real process-kill recovery checks. A complete marker is checked against actual identities, counters and table hashes before any publication. The strict read-only reader requires that marker and the exact external manifest.

`build/horizon-finish-baseline.json` pins all 2,314 baseline inputs: 2,312 previously accepted inputs and their acceptance/rerun evidence. New source is frozen separately in `build/horizon-finish-implementation.json`. Accepted old sources and artifacts are never edited.

The explicitly versioned recovery fixture uses the first selected root by default, with requested H14 at 25,000,000 then 250,000,000 nodes. This causes a genuine initial budget rejection and exercises fallback. Its paths stay under `build/`, settings and identity differ from production, and production admission rejects fixture settings. No altered state or fabricated label is used.

The new API is `load_rows(path)->(rows,stores,manifest)`: `rows` contains all six original wrappers. The unchanged prior tables are `h8_references`, `h10_references`, `h12_references`, `prior_h12_attempts`, `prior_h14_attempts` and `prior_h14_labels`. New tables are `tier1_attempts`, `tier1_labels`, `tier2_attempts` and `tier2_labels`. Each table has `state`, canonical JSON `body` and SHA-256 `hash`. New attempt bodies add `schema`, `tier` and `node_budget` to the old H14 attempt shape; history remains embedded. `combined_labels(stores)` merges the unchanged old H14 item with completed new tier labels. The selected five keys are frozen in the registry's `state_keys`.

The CLI is `python tools/horizon-finish.py plan|freeze|tier1|tier2|all|verify`. `all` resumes or repairs an absent external publication from a valid committed marker; `verify` requires an existing publication. No teacher calls occur on a completed rerun. The author report has four methods; independent checks, full production counts, descriptive six-root comparison and zero-search stable-rerun evidence are recorded separately.
